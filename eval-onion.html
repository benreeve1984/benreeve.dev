A simple map of AI evaluation

Every eval needs an input, an output and a way to score it.

Those three parts stay the same. As you test more of the system, the input comes from a more realistic source, the output includes more than text, and the scoring has more to check. Tools can run and display evals, but they cannot supply your data, copy your systems or decide what "good" means for your business.

The five layers

Five layers, one core

Read each column from top to bottom. The input, output and scorer are always there. The last two rows show the extra work and the common failure points.

L0STATIC

Fixed questions, fixed answers, simple checks

This is a standard benchmark. The questions and answers sit in a file, and the model answers each one. It tests the model, not the full product. The test also gets easier over time as models improve or see the questions in training data.

What this layer needs

  • buildA question bank with approved answers. Public benchmarks cover general skills. You must write the questions about your business.
  • buyA runner that reads each row, calls the model, stores the result and compares runs.
  • watchRun each test more than once. Model answers vary, so one run of a small test can move by several points.
Internal SQL / document agent200 business questions with a known correct number ("Q3 revenue in EMEA"). Scorer: does the returned number match to two decimals?
Customer-facing support agent150 FAQ-style questions with the policy clause they should cite. Scorer: does the reply contain the clause reference?

What this layer misses

  • It scores a model, not your product. Your product has a prompt, retrieval, tools and policies wrapped around the model.
  • Public tests lose value. Top models may all score well, or the questions may appear in training data. Artificial Analysis removed MMLU-Pro, AIME 2025 and LiveCodeBench when they stopped separating the best models. LiveBench adds new questions each month.
  • Most product outputs are too open-ended for an exact text check.
When a benchmark becomes a target, its score can rise even if the model has not improved more broadly.Micah Hill-Smith, Artificial Analysis, on Latent Space
A reasoning model can give different answers on repeated runs. Artificial Analysis repeats each benchmark and reports a ±1% confidence range.Artificial Analysis
L1JUDGED

For open-ended answers, use a model to judge the result

A good email, summary or SQL query can take many forms. An exact text check will not work. A second model can judge the answer against clear rules, but first you need to check that its decisions match those of people who know the work.

What this layer adds

  • buildClear rules that define a good answer for this task. Generic "helpfulness" or "hallucination" scores rarely match a real business need.
  • buildA sample marked by a subject expert, plus a measure of how often the expert and model agree.
  • buyJudge templates, prompt testing tools and side-by-side run comparisons.
Internal SQL / document agent"Summarise the contract's termination terms." The judge checks that all four clauses are present and no dates are invented. An in-house lawyer marks 100 examples so the team can test the judge.
Customer-facing support agentReply to a complaint. Judge checks tone, policy accuracy, no promises the policy doesn't allow. A team lead from the contact centre labels the sample.

What this layer misses

  • It still tests one request and one answer. An agent may make several calls, look up data and take actions.
  • The judge only sees the answer. It cannot tell whether the agent ran a query or only claimed it did.
  • Model judges cost money. Using several large models to grade every answer can multiply the token bill.
A 1–5 score is too vague unless each number has a clear meaning for the task.Hamel Husain, "Creating a LLM-as-a-Judge That Drives Business Results"
If high scores do not match good answers, change the checks or the test cases.Braintrust docs, "Interpret results"
Artificial Analysis compares work in pairs with three large judge models, then checks the ranking against human experts.Artificial Analysis, GDPval-AA
L2AGENT WORK

For an agent, the output is the answer and the record of its work

An agent chooses its own steps. It may search a document, run a query, call an API and try again. To test it well, keep a structured record of every model call, tool call, delay and cost. Then check the steps that matter as well as the final answer.

What this layer adds

  • buildTracing inside the agent. Record every model and tool call with its time, token use and inputs. A vendor gives you a library, but your engineers still add it to the app.
  • buildChecks for the errors you care about, plus approved labels for choices such as which tool the agent should use.
  • buildRepeat runs and a reliability measure. An agent that passes half the time has less than a 1 in 256 chance of passing eight runs in a row.
  • buyA trace store, a timeline, step-by-step time and cost views, and comparisons between runs.
Internal SQL / document agentDid it query the right table? Was the SQL syntactically valid on first try? How much of the 6 s was the database vs the model? Did the number match finance's figure?
Customer-facing support agentDid it check the order status before promising a refund? Did it call the refund tool with the correct order ID? Was the customer's issue actually resolved by the end of the thread, not just each turn answered?

What this layer misses

  • A trace records what the agent did, but not whether the real result exists. A message that says "Your refund has been processed" does not prove that the ledger contains a refund.
  • The agent needs something safe to act on during a test: a database, documents or a customer. Layer 3 supplies those test versions.
A booking message is not proof of a booking. Check that the reservation exists in the database.Anthropic Engineering, "Demystifying evals for AI agents"
The same trace store supports both evals and live monitoring, which is why it is central to these products.Phil Hetzel, Braintrust
An agent can answer most turns well and still fail to solve the customer's problem.LangChain, "Evaluating AI Agents at the Run, Trace, and Thread Level"
L3TEST WORLD

Give the agent a safe copy of the systems it uses

In a test, the agent cannot use live customer data or change production systems. It needs a database that resets after each run, a fixed set of documents, a model that can play the customer and a clean sandbox for every attempt. Building and maintaining this test world is usually the largest part of the work.

What this layer adds

  • buildA database copy with the same structure, useful sample data, no private details and a reliable reset. The same agent framework scores about 91% on the simple Spider 1.0 test but about 21% on Spider 2.0, which uses large business databases.
  • buildA model that plays the customer in conversation tests. τ-bench checks whether the database ends in the expected state. τ²-bench found that agents score much lower when the test customer can also take actions. Results also change with the quality of the customer simulation.
  • buildA dated copy of documents or web content, with a schedule for updates. Live-web agents may find the answer key online. Blocking one site cut accuracy on affected questions by about 15%.
  • buildTasks with goals you can verify. For SWE-bench Verified, 93 developers checked 1,699 tasks. Removing broken tasks roughly doubled the measured score.
  • buySandbox hosting and software that runs each test in isolation.
Internal SQL / document agentA test warehouse with last quarter's data and fake personal details; contract files fixed at 1 July; questions with answers approved by finance. Reset it after every run so a stray UPDATE cannot affect the next test.
Customer-facing support agentA test CRM and order system; a model playing "angry customer, order 4471, wants a late refund"; policy documents fixed at one version. After the run, check whether the refund exists, has the right amount and follows the policy.

What this layer misses

  • The copy gets out of date as databases, policies and customer needs change. Give someone clear responsibility for keeping it current.
  • It only contains failures you thought to test. Real users will find new ones. Layer 4 brings those cases back into the test set.
  • Agent tests can run for a long time. Running many isolated sandboxes at once needs its own systems and budget.
Start every run from a clean test world. Leftover data can make later runs fail for the wrong reason.Anthropic Engineering
Prime Intellect built a system that can start more than 4,000 isolated sandboxes at once for large test runs.Prime Intellect, INTELLECT-3
Keep each test world as a versioned package. This makes changes easier to track and compare.Prime Intellect
Even a simple one-turn training task can grow into a full codebase once the test world is realistic.Community guide to the Environments Hub
L4PRODUCTION

Review live traffic and turn failures into new tests

Offline tests catch known problems. Live use reveals the ones you missed. Run the same checks on a sample of real traces, ask people to review important cases and add failures to the offline test set. Cost rises with the number of traces you store and score.

What this layer adds

  • buyRules for sampling and scoring live traces, dashboards, slow-step views, review queues and an easy way to add a trace to a test set.
  • buildA sampling policy, judge prompts and a review rota. A subject expert must read traces each week and act on what they find.
  • buildA custom review screen when the vendor's generic queue does not fit the work.
  • watchDo not treat a green dashboard as proof that the product works. People still need to inspect real cases.
Internal SQL / document agentEvery analyst query is traced. 5 % random plus anything over 10 s or with a thumbs-down goes to the judge. A finance analyst reviews 30 a week. Queries against the wrong fiscal calendar become a new test cluster in L3.
Customer-facing support agentScore all conversations for policy compliance each night. Review every conversation that mentions "refund". Contact-centre leads check cases where people and the judge disagree. Show slow first replies by step so engineers can see whether the CRM lookup or the model caused the delay.

Two architectures for the same loop

  • Score stored traces on the platform. Braintrust, LangSmith and Langfuse run the judge over traces they store. This is easy to set up. Depending on the product, the store is hosted by the vendor or by you.
  • Score inside your app and send the results. With Pydantic Logfire, the same Evaluator code can run offline and on a sample of live requests. It sends standard OpenTelemetry data, so you can use another compatible store.
  • The lock-in question is about the trace store, not the eval loop. Ask any vendor: can we export every trace and score in a standard format?
A useful live trace can become an offline test, and that test can prevent the same failure later.Braintrust, "How to evaluate LLMs and agents in production"
Use the same scoring rules in offline tests and on sampled live traffic.Pydantic, "Online evals in Logfire"
Reading failed cases and grouping their causes is one of the best ways to improve an AI product.Hamel Husain, "A Field Guide to Rapidly Improving AI Products"
The decision

A tool covers only part of the work

Each label is something the layer needs. You can buy the blue items. The striped items depend on your data, systems and experts, so your team must build and maintain them.

L1JUDGED

What a product gives you

  • A ready-made eval loop. Free libraries such as Braintrust autoevals, Pydantic Evals and Inspect provide this too.
  • A place to keep traces and scores, with a screen that takes you from a falling score to the exact slow or wrong step.
  • Shared tools for testing prompts, reviewing answers and keeping prompt versions. These let product staff and subject experts work alongside engineers.
  • Pricing usually follows production use. Braintrust has plans from $0 to $249 a month, then charges for trace data and scores. Traffic and sampling choices drive the bill.

What your team still builds

  • The test data. It should come from real failures, carry labels from your experts and change as the product changes.
  • The checks. Write them for errors you have seen. Generic scores rarely tell you whether the product did its job.
  • The test world. Keep a working copy of the systems the agent uses, such as a test warehouse and fixed documents, or a CRM sandbox and a test customer.
  • The tracing and weekly routine. Someone reads traces, checks judge disagreements and turns failures into tests.

What this means for the decision

  1. Buy the trace store and review screens if they save time. The eval loop itself is available in free, open-source libraries. Paid products are most useful for storing traces, finding a bad step and helping several people review the same work.
  2. Put most of the budget into your own test data and systems. Your team still needs to write the rules, add tracing, build the test database, create test customers and review results. A realistic test world is what turns a model score into evidence about the product.
  3. Ask where the trace data lives and how to export it. Braintrust and LangSmith can be quick to start. Tools built on OpenTelemetry, including Logfire and Phoenix, make it easier to move data. Langfuse can be self-hosted. Require a full export whichever tool you choose.
  4. Name the people who will read the traces. A subject expert should review real cases every week and mark them pass or fail. Without that routine, the dashboard will not improve the product.
